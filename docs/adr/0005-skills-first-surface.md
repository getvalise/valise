# 0005. Skills first: one tool per skill, and the SEP-2640 URIs as written

Date: 2026-10-15
Status: accepted

## Context

ADR-0003 froze eleven tools and put skills behind two of them: `list_skills` to see what exists, `get_skill` to pull one body. In a real client that costs a round trip the model has to think to make. Nothing in `tools/list` says a skill exists, so the model has to already suspect Valise has one before it looks. Measured against the alternative — the skill's own description sitting in the tool list where the model reads it anyway — the listing tool loses.

The second problem is narrower and worse. V1-4 shipped resources at `skill://skills/{name}`, a URI we invented. SEP-2640 reached Final on 2026-09-13 and defines `skill://{name}/SKILL.md`, siblings for supporting files, `skill://index.json` for discovery, and the methods `skills/list` and `skills/get` under the extension id `io.modelcontextprotocol/skills`. A host that resolves `references/checklist.md` relative to our URI lands on `skill://skills/references/checklist.md`, which is nothing. V1-4's "two doors" box was ticked against a door that does not open.

## Decision

- Every published skill is also registered as its own tool, named `skill_{name}`. Its description is the skill's frontmatter description, unchanged, plus one sentence saying the body arrives on call. The body is not in `tools/list`; that is the progressive disclosure the whole convention exists for.
- Per-skill tools take no arguments and require `skills:read`, derived from the `skill_` prefix rather than enumerated. `list_skills` and `get_skill` stay, because a client with a tool-count limit still needs a way to reach a skill it cannot see.
- Resources move to the scheme the extension defines: `skill://{name}/SKILL.md`, `skill://{name}/{path}` per bundled file, `skill://index.json` for the index.
- `io.modelcontextprotocol/skills` is declared next to `resources` in the server capabilities, and `skills/list` and `skills/get` are implemented as low-level request handlers, since the installed SDK has no skills vocabulary. Each entry carries full frontmatter and a manifest of `{uri, digest, size}` over `SKILL.md` and every bundled file, computed from the bytes actually served.
- A `skill://` URI resolves only through the published manifest of the head version. A path the manifest does not name cannot reach an R2 object.

## Amendments

- 2026-11-15, a capped tool list. Owner, 2026-11-15, in a Claude Code session: cap the per-skill tools by recent use, chosen over removing them all and over trimming each one. `tools/list` lists at most `SKILL_TOOL_LIMIT`, 10, `skill_{name}` tools: the enabled skills with the most loads through a `skill_` tool or `get_skill` in the last 30 days, then the newest head version, then by name. `rankSkillTools` in `app/concepts/skills.ts` reads both kinds of load through the `mcp_calls_tool_at` index. Prompt and resource loads are not counted, because neither records a tool to index on. Every other request still registers every enabled skill's tool, so a client holding an older list can call any skill it saw there. `list_skills` now says only the most-used skills also appear as tools. Evidence, production `mcp_calls` over the 30 days to 2026-11-15: 16 skill tools took 73 calls between them and `get_skill` took 90, while each of 5,619 `tools/list` results carried every enabled skill at about 1.5 KB each, 420 bytes of it model-visible. Ranked by those loads, the top ten skills account for 108 of 165. This is the per-skill switch the Consequences below expected past twenty skills, made automatic rather than a console setting. A skill that falls off the list climbs back only through `get_skill`, or through its tool in a client's older list. That is the cost of a list that tracks use without anyone curating it.

- 2026-10-19. `read_skill_file(name, path)` gives tool-only clients supporting-file access without a resource-reading bridge. It shares `readSkillFile` with resources, checks `skills:read`, and returns UTF-8 text only. SKILL.md stays behind the skill tools and prompts; binary files stay behind `resources/read`. The path must be in the active head's published manifest, so disabled/deleted skills and unlisted R2 objects remain unreachable. Prompt file guidance names both routes. Tool-choice cases `skill-file-needed` and `skill-file-unneeded` distinguish a referenced dependency from speculative file loading.

- 2026-10-19. Each enabled, non-deleted skill is also an MCP prompt named by its skill name. `prompts/list` returns names and descriptions; `prompts/get` reads the current head and returns its unchanged SKILL.md text as a user message, with a separate list of supporting-file resource URIs when present. Both methods require `skills:read` and use the ordinary observed dispatch path. Prompt catalogs are resolved per request; a stale command cannot retrieve a disabled or deleted skill. The server advertises prompts even for an empty catalog, without claiming push refresh notifications. Clients own command naming and refresh: the probes in PR #132 found OpenCode's `server:name` registry and Claude's `mcp__server__name` invocation, not native skill registration. Tools, resources, and extension handlers remain the automatic-discovery and file-access surfaces.

- 2026-10-16, V1-16. Skills can arrive from skills.sh as well as from the publish box. The import goes through `publishSkill`, so an imported skill is an ordinary v1 with an ordinary bundle and all three doors; the only new state is `skills.source` and `skills.source_hash`, which record where it came from and what it was. skills.sh carries no licence field and its terms push the question onto the upstream repository, so the licence shown is whatever the SKILL.md states and "not stated" when it states nothing.
- 2026-10-18. The console edits a skill's SKILL.md in place: review posts a diff against the head without writing, and publish writes version N+1 through the same path as `publishSkill`. The edit keeps the frontmatter `name`, because the name is the skill's identity; a rename is a different flow. The bundle is carried by manifest rather than copied, since R2 objects under a version key are written once and never replaced, so version N+1 points at the keys version N wrote. Built-in and imported skills are editable and keep `source` and `source_hash`. A built-in edited here already reads as held, because its head no longer matches `source_hash`; an imported one will read the same way once upstream checks compare against it.
- 2026-10-18. Skills can also come from a GitHub file, folder or repository URL. The Worker downloads the repository once as a tarball from `codeload.github.com` and reads it in a streaming tar reader. It makes no API call per file, because unauthenticated API calls are capped at 60 an hour per IP and Workers share their outbound IPs. `source` is `github:owner/repo@<commit-sha>:<path>`, with `.` for a skill at the root. The sha comes from the pax global header `git archive` writes, so a preview and its publish read the same commit. `source_hash` is `bundleDigest`: the sha256 over the sorted `path\0sha256(content)` lines of SKILL.md and every bundled file. An update check can then recompute it from a fresh download and compare. A repository lists each skill once. Copies with the same name and body collapse to the path a `.claude-plugin/marketplace.json` plugin points at, following symlinks for that lookup only. Otherwise the shortest path wins. Symlinked folders are skipped. Private repositories are not supported.
- 2026-10-18. Imported skills are checked for upstream updates. The check runs on demand from the skill dialog and from the existing daily cron. It fetches one tarball per GitHub repository at its default branch and one download per skills.sh skill. It stores the digest it found in `skills.upstream_hash`, with `upstream_source` naming what an update would import and `upstream_checked_at`, so the list and the dialog read columns rather than the network. An update is available when `upstream_hash` differs from `source_hash`. "Review update" opens the Add skill preview on the upstream copy, which shows the diff against the head. `skills.source_version_id` records the version an import wrote. A head past it was edited here, and the dialog says so before an update replaces that edit as the head. A publish whose body matches the head but whose files differ is now a new version rather than a no-op, so an upstream change to a bundled script lands. Built-ins stay with the deploy-time sync.
- 2026-10-18. The console changes many skills at once and can delete one. Ticked rows post one `change` (enable, disable, delete or restore) through `changeSkills`, which writes every row and its projection in one batch. Delete sets `skills.deleted_at`, which every agent door and the default console list already filtered on; versions, bundles and usage stay, and "Show deleted (n)" brings the rows back into the list with Restore beside them. A restored skill comes back in the state it left, so a skill that was off is still off. A publish over a deleted name, by hand, import or MCP, clears `deleted_at` and lands as the next version rather than colliding with the unique index on `name`; a word-for-word republish restores the head without a version. Built-ins cannot be deleted, because the deploy-time sync would publish them straight back; they can be switched off. None of this is an MCP tool: an agent has no reason to delete a skill, and a console-only delete keeps one from doing it by mistake.
- 2026-10-18. A repository listing imports many skills in one post. The listing is a checklist pinned to the commit it read, and `importGithubSkills` downloads every ticked folder from that one tarball and publishes each through `publishSkill`, the same as a single import. Each row reads `added` when a live skill came from this repository and folder at any commit, and `taken` when a live skill of that name came from anywhere else or was written here. A taken name cannot be ticked, and a batch skips it rather than publish over another skill's history. Deleted skills count as neither, so importing one restores it. New rows start ticked, added rows unticked, and the person's ticks survive an import that lands. A folder that fails to read or validate, such as one bundling a PNG, is reported by path without stopping the rest. Marketplace plugins whose `source` names another repository are not followed.
- 2026-10-18. A bundled file need not be text. The GitHub reader keeps a file that is not UTF-8 as its bytes, `BundleFile.content` is a string or bytes, and every digest and size is computed over the bytes, so each text digest already recorded in `source_hash` and the manifests is unchanged. A `skill://` read answers `text` when the stored bytes decode as UTF-8 and a base64 `blob` otherwise, with the type taken from the extension. SKILL.md itself must be text. A GitHub skill may carry up to 10 MiB, the object store's limit from ADR-0011, because an example image runs past the 2MB that skills.sh, which serves only text, keeps. MCP `publish_skill` still takes text files only.
- 2026-10-19. An imported skill can follow upstream without review. `skills.auto_update` is off by default, because following puts a third party's text in front of every connected agent; the owner turns it on per skill or for ticked rows (owner, 2026-10-18). The upstream check, from the daily cron or a dialog's "Check for updates", already downloads the newer bundle, so when `upstream_hash` differs from `source_hash` and the skill auto-updates it publishes that bundle through `publishSkill` as `auto-update`, which moves `source_hash` and `source_version_id` with it. A skill edited here is held, never overwritten: it shows the update and waits for "Review update". The console's Update applies available updates to the ticked rows whatever their setting, and holds edited ones the same way, since one press over many rows is not a review of each diff. Every applied update is an ordinary version, so going back is publishing the one before. Built-ins and skills written here have no upstream and cannot auto-update.

## Consequences

Gained: a model sees the skills without being told they exist, and a host that speaks SEP-2640 can verify what it loaded. Given up: the tool list grows by one per skill, which will need a per-skill switch somewhere north of twenty skills; the manifest is only as honest as the head version, so a pinned older version is reachable through `get_skill` but not through `skill://`. Inherited: the extension is Final but host support is partial, so the tool wrapper is the surface that actually gets used today and the resources are the surface that will.
